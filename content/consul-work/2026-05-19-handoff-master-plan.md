# 事業承継・引き継ぎマスタープラン（バス係数=1 の解消）

**作成: 2026-05-19 / オーナー: 由井辰美（クライミングコンサル）**

## この文書の目的

クライアント全社の開発・運用を由井辰美が一人で担っている。
仕様書は渡しているが、**「動かす権利」と「鍵」が由井の頭とローカルPCにしかない**。
由井が不在（病気・事故・廃業）になった瞬間、クライアントは自社サービスを
復旧・改修できなくなる。これを**最小工数で**回避する。

> いわゆる「バス係数（Bus factor）= 1」問題。
> 担当者が1人 = その1人がバスに轢かれたら全停止。これを 2 以上にする。

## 本質：足りないのは「仕様書」ではなく「権利と鍵の継承経路」

由井が渡しているのは *What*（何を作ったか）。
引き継ぎに本当に要るのは *Who owns it & How to access*（誰の所有物で・どう入るか）。
後者は1事業あたり A4 1〜2枚で書ききれる。ツール導入も組織変更もほぼ不要。

シークレット台帳（[2026-05-17-secrets-inventory.md](2026-05-17-secrets-inventory.md)）は
「鍵の地図」として既にある。**地図はあるが宝箱の鍵が由井のポケットの中**。
鍵そのものの継承経路を作るのが本プラン。

## 3つの致命的単一障害点と対策（CEO 決定済み・2026-05-19）

| # | 単一障害点 | 対策（決定） | 状態 |
|---|---|---|---|
| 1 | **GitHub アカウント1つ（個人）** = 凍結で全社コード同時消失 | **GitHub Organization 化**。Org に全リポ移管、Owner を2名以上に | 未着手 |
| 2 | **API キー・各サービスのログインが由井のローカル/頭にしかない** | **Bitwarden 無料 Organization**。Collection を事業別に。Emergency Access で死活時に継承 | 未着手 |

ドメイン/DNS の所有者不明も同格の致命傷だが、上記3つに紐づけて台帳で回収する。

## フェーズ別実行計画（効果の大きい順）

### フェーズ0：Supabase 実態調査（最優先・他の判断の前提）

複合 Project に何社が相乗りしているか不明なままでは引き継ぎ台帳が書けない
（「このDBが死ぬと何社が止まるか」が説明できない）。

- [ ] 各事業フォルダの Supabase 接続先（プロジェクト参照ID / URL）を棚卸し
- [ ] 「企業別 Project」と「複合 Project」を一覧化
- [ ] 複合 Project ごとに「どのテーブル/スキーマがどの事業か」を特定
- [ ] 複合の相乗り社数・解約時の波及範囲を1表にまとめる
- [ ] → 結果を [work/2026-05-19-supabase-tenancy-audit.md](work/2026-05-19-supabase-tenancy-audit.md) に出力
- [ ] その上で「分離するか・台帳明記で済ますか」を CEO 判断

**この調査はコードベース横断スキャンになるため Codex 併用を検討**
（入口判定：5ファイル以上横断 → codex:codex-rescue サブエージェント候補）。

### フェーズ1：GitHub Organization 化（単一障害点#1の根本解決・無料）

**所要：30〜60分。コスト0円。** 効果が最大かつ最も簡単。

1. github.com/account/organizations/new → **Free プラン**で Org 作成
   （Org 名案：`climbing-consul` など由井の屋号ベース。クライアント名は出さない）
2. 既存リポを Org へ Transfer（Settings > General > Transfer ownership）
   - リポURLは変わるが GitHub が自動リダイレクト。Vercel 連携は再リンク要（後述）
3. **Owner を2名以上に**：
   - 由井（本人）
   - 「予備管理者」：信頼できる第三者 / 各クライアントの情報システム担当 / 法人なら共同代表
   - ※予備管理者がいない場合でも、Org 化するだけで「アカウント凍結 ≠ 全消失」になる
4. Vercel との再連携：Org 移管後、各 Vercel Project の Git 連携を Org リポに貼り直す
5. → 完了後、本プランのチェックを更新し台帳（フェーズ3）に Org 名と Owner を記載

**注意**：プライベートリポは Org Free でも無制限・無料。Actions も公開リポ無制限/
プライベート2000分/月（現状の cron 規模なら収まる）。**有料化不要**。

### フェーズ2：Bitwarden 無料 Organization（単一障害点#2の根本解決・無料）

**所要：1〜2時間（鍵の登録含む）。コスト0円。**

なぜ「保管庫を5つ目に増やすな」と過去に却下したか（2026-05-17 の判断）と矛盾しないか：
→ **矛盾しない**。あれは「鍵の実値の散在を1つに集約せよ」という話。
Bitwarden は *散在している実値の参照と緊急継承* のレイヤであって、
Vercel/Supabase/GitHub Secrets の値を**置き換える**のではなく、
「どこから取り出すか」と「由井死活時に誰が取り出せるか」を一元化する継承装置。
保管庫を増やすのではなく、4保管庫への**アクセス権を継承可能にする**のが役割。

手順：
1. bitwarden.com → 無料アカウント作成 → **Free Organization** 作成（2ユーザーまで無料）
2. Collection を作る（鍵の実値そのものではなく「アクセス手段」を入れる）：
   - `_共通`：GitHub Org の Owner ログイン、Vercel Team ログイン、ドメインレジストラ
   - `ai-hub` / `トラスト` / `ビジネス21` / `みんなのWA` / `ClimbHero` … 事業別
   - 各 Collection に：そのサービスの管理画面ログイン情報、復旧手順リンク
3. **Emergency Access（緊急アクセス）を設定**：
   - 予備管理者 or クライアント代表を Emergency Contact に指定
   - 待機期間（例：7日）後に自動で金庫アクセス権が移譲される設定
   - = 由井が応答不能になっても、7日後にクライアントが鍵を取り出せる
4. シークレット台帳（secrets-inventory）の各行に「Bitwarden の○○ Collection 参照」を追記
   - 台帳 = 地図、Bitwarden = 鍵束、両者をリンクで接続

**Free の制約と十分性**：無料 Org は 2 ユーザー・2 Collection 制限がある場合がある
（プラン仕様は登録時に要確認）。制限に当たる場合の代替：
- 個人 Vault + Emergency Access のみで運用（Collection 分割せずメモ整理）
- または有料（Vercel が既に有料なので Bitwarden 数ドルは許容範囲・1Password Teams も可）
- → 登録時に Free 枠を確認し、足りなければ CEO に有料化を諮る

### フェーズ3：引き継ぎ台帳（事業別 A4 1〜2枚）の作成

シークレット台帳が「鍵の地図」なら、これは**「事業の全体引き継ぎ書」**。
1事業1ファイル：`work/2026-05-19-handoff-<事業略称>.md`。テンプレは本文書末尾。

埋める順（影響度順）：トラスト → ビジネス21 → みんなのWA → ai-hub →
ClimbHero → Notエステ → Nデザイン → ファディー →（カラーミー/Shopify系は最後）

### フェーズ4：クライアントへの説明と物理的受け渡し

技術的に整っても、クライアントが「自分の資産がどこにあるか」を知らないと無意味。

- [ ] 各クライアントに「あなたの会社のシステム引き継ぎ書」を1部渡す（紙 or PDF）
- [ ] 内容：何のサービスがどこで動き、誰が鍵を持ち、由井不在時にどう発動するか
- [ ] Bitwarden Emergency Access の Contact になってもらう（or 予備管理者を立てる）
- [ ] 契約書に「ソースコード・アカウントの所有権はクライアントに帰属」と明記
      （[クライミングコンサル発行者情報.md] の契約雛形に承継条項を追加検討 → cfo/advisor）

## 最小で「明日から効く」アクション（これだけでバス係数 2 になる）

工数を1日に絞るなら、以下4つだけで単一障害点は実質解消する：

1. **GitHub Org 作成 + 全リポ移管**（フェーズ1）— 半日・無料・効果最大
2. **Bitwarden 無料 + Emergency Access**（フェーズ2の3まで）— 1時間
3. **シークレット台帳に「実値の取り出し方」を1列追記**（既存ファイル更新のみ）
4. **トラスト1社だけ引き継ぎ台帳を試作**（テンプレ検証 → 横展開）

残り（全事業の台帳・Supabase分離・契約条項）は走りながら埋める。

## 引き継ぎ台帳テンプレート（フェーズ3で各事業に複製）

```markdown
# 引き継ぎ書：<事業名>（<クライアント正式名>）

## 1. この事業は何か
- サービス概要（1〜2行）／本番URL／クライアント連絡先・担当者
- 契約形態（受託/保守）・所有権の帰属

## 2. 動いている場所（インフラ地図）
| レイヤ | サービス | 識別子 | 管理アカウント |
|---|---|---|---|
| ソース | GitHub | <Org>/<repo> | <Org Owner> |
| ホスティング | Vercel | Team名/Project名 | <Vercel Team> |
| ドメイン/DNS | <レジストラ> | <ドメイン> | <ログイン手段→Bitwarden参照> |
| DB | Supabase | <プロジェクト参照ID>（企業別/複合） | <取り出し方> |
| 外部API | LINE/Gemini等 | <発行元アカウント> | <Bitwarden参照> |

## 3. 鍵の取り出し方
- 環境変数一覧 → secrets-inventory.md の該当セクション参照
- 実値 → Bitwarden Collection「<事業名>」参照
- 由井不在時 → Emergency Access が <待機日数> 後に発動

## 4. 復旧手順（3〜5行）
1. GitHub Org にアクセス（Owner権限）
2. Vercel Team にログイン → main push で自動デプロイ
3. 環境変数は Vercel Dashboard に設定済（変更時は secrets-inventory 手順）
4. DB は Supabase（バックアップ：daily 7日/PITR有無を明記）

## 5. 既知の注意点・地雷
- この事業固有の罠（複合DB相乗り・期限つきトークン等）
```
