## 1. エグゼクティブサマリ（3行）

1. **1〜2年（〜2028年5月）撤退は約50〜60%の確率で破綻する**。最大の律速要因は「Next.js + Supabase + 業務理解 + 月10〜25万円の保守単価」を同時に満たす個人/小規模事業者がフリーランス市場の単価分布（平均月76〜94万円）と**構造的に噛み合っていない**こと。
2. **トラスト（24時間SLA・福祉インフラ・LINE Bot・Anthropic API・夜間障害不可）は B では現実的に出口がない**。1事業者完結の譲渡は不可能。Bを試みるなら個人ではなく**小規模制作会社（2〜5名・有事代替要員あり）**に限定、それも難航する前提で**C（SaaS移行＝らくしふ＋市販シフトソフト）への計画的撤退を本命**に切り替えるべき。
3. **5事業を1人で引き受ける後継は実在しない前提で組み立て**、Notエステ/N-デザイン/ファディーの「サイト系3本」を1グループ、ビジネス21/トラストの「業務系2本」を別グループに分ける**2グループ譲渡が現実解**。それでも 2028 Q1 完了は厳しく、**2028 Q4〜2029 Q2 延長を覚悟したうえで「段階的撤退」**を組むべき。

## 2. 論点1: 後継エンジニア候補者像の定義（最重要）

### 2-1. 個人 vs 中小制作会社 vs 中堅制作会社 — 現実評価

| 規模 | 月間保守原資想定 | 引受可能性 | 評価 |
|---|---|---|---|
| **個人フリーランス**（1名） | 各事業 月10〜20万円 × 5事業 = **月50〜100万円総額** | **❌ 不可** | フリーランス Next.js 平均単価は月76〜94万円（freelance-start.com / sokudan）。5事業並列保守＝月稼働160時間想定で1事業者完結なら月140万円〜になる。**クライアントの保守予算とフリーランス相場は乖離**（5事業合算で月50〜100万円程度しか出ない想定）。さらに24時間SLA（トラスト）に1人で耐えるのは**休暇取得が原理的に不可**で持続不能 |
| **中小制作会社（2〜5名）** | 月10〜25万円 × 事業数 | **△ 第一候補** | 5名規模なら相互バックアップ可・夜間オンコール輪番可。利益率を取りつつ業務継承を引き受ける動機があるのは「**既に Vercel+Supabase で受託しており新規顧客を求めている地方制作会社**」。実在するが**滋賀県内には事実上ゼロ**（TypeScript×Next.js都道府県別案件数で滋賀は上位10にも入らず） |
| **中堅制作会社（10名以上）** | 月15〜30万円 × 事業数 | **△△ 単価で蹴られる** | 案件単価が合わない。中堅は最低月50万円以上の継続案件を求める。彼らが乗るとしたら**事業譲渡対価込みのM&A的取引**（保守ではなく事業買収）になり、CEOの「綺麗に手放す」目的とは合うが、買収価格交渉が長期化 |

### 2-2. 必須スキル

**必須（外せない）**:
- Next.js 15 App Router 実務経験 1年以上
- Supabase（Auth/Storage/RLS/Postgres）実務経験
- Vercel デプロイ運用経験（環境変数・PR プレビュー）
- TypeScript 業務レベル
- Git/GitHub 標準ワークフロー
- **個人事業主登録 or 法人格**（インボイス T登録あり望ましい）

**業務系2本のみ追加必須**:
- LINE Messaging API + LIFF 実装経験（トラスト）
- Anthropic SDK or OpenAI SDK 実装経験（トラスト）
- 個人情報保護法・労働基準法の基礎理解（ビジネス21・トラスト）

### 2-3. 必須でない方が良いスキル（過剰スペックは月額に合わない）

- React Native / Flutter（不要）
- Kubernetes / Docker Swarm 運用（Vercel に乗っているので不要）
- Rails / Django / Spring 等のレガシースタック（混在は不利）
- AWS フルスタック資格（過剰）
- **平均月単価70〜90万円層**は引き受けない（単価不一致で破談）

### 2-4. 福祉24時間SLA（トラスト）— 引受可能層の実在性

**結論: 個人では実在しない。2〜5名規模の制作会社で「すでに福祉/医療系業務委託を持っている事業者」のみ**。

理由:
1. **夜間障害対応**: 1人事業者は休暇・体調不良時に対応不能。法人化していて代替要員がいる事業者のみ
2. **福祉業界の慣性**: 「ほのぼの」（コニカミノルタ / リコー / キヤノンMJ）など既存大手SaaSがメイン。Next.js カスタム実装を引き受けたい後継は本来「市販SaaSへ移行してくれ」と言う立場
3. **責任の重さ**: 利用者個人情報・薬剤情報・障害区分情報を扱う。**P5000万円規模の賠償保険加入が現実的に必要**で、個人事業者の保険料負担で破綻する

→ **トラストは戦略B 単独では出口設計が成立しない**。Cハイブリッド前提（次節）。

### 2-5. 業務理解の重みづけ

| 事業 | 業務理解の重み | 補足 |
|---|---|---|
| Notエステ | 低（30%） | エステ業界知識は薄くてもUI/UX寄りで補える |
| N-デザイン | 低（30%） | 工務店業界の専門性は施工事例ベタ書きで対応可 |
| ファディー | 低（再生成中・要件まだ柔軟） | 完成形によって変動 |
| **ビジネス21** | **高（70%）** | 監理団体・特定技能・育成就労（JITCO 2026/4 制度改正）の理解必須。誤った機能実装は監理団体の許可取消リスクに直結 |
| **トラスト** | **高（70%）** | 障害福祉サービス・障害者総合支援法・配置基準・夜勤労務管理を理解しないとシフトロジックの正当性が保証できない |

### 2-6. 1人で5事業引受は現実的か

**❌ 非現実的**。理由3つ:

1. **稼働量**: 5事業 月160時間 ≒ ほぼフルタイム。これを月50〜100万円で引き受ける個人は単価相場から外れる
2. **業務理解の幅**: エステ・建築・監理団体・福祉・地域コミュニティを全部キャッチアップは非現実的
3. **障害時の重複**: 5事業のうち2つが同時障害したら1人では対応不能

→ **必ず複数の後継に分散すべき**。最適分割は次節。

### 2-7. 推奨分割パターン（advisor の提案）

```
グループ1: サイト系3本（Notエステ / N-デザイン / ファディー）
  → 中小制作会社A（2〜5名・地方or リモート）
  → 月額 各 8〜15万円 × 3 = 月24〜45万円
  → 業務理解の重みが低い・スタックほぼ同一でスケールメリット出る

グループ2: ビジネス21 単独
  → 中小制作会社B（監理団体or 行政系 SaaS 経験者）
  → 月額 20〜35万円
  → コンプライアンス重視・他事業と束ねない方が安全

グループ3: トラスト 単独
  → 中小制作会社C（福祉/医療系 受託経験者）or **戦略C へ移行**
  → 月額 25〜40万円
  → 24時間SLA・個人情報・福祉法規が突出して重い
```

**3グループ並行探索**。1グループ確定したら次へ、ではなく**並行で動かないと2028 Q1 に間に合わない**。

## 4. 論点3: 部分受託テストの設計

### 4-1. リスクの低い順にタスクを振る

| ステップ | タスク種別 | 期間 | 評価対象 | 落とし所 |
|---|---|---|---|---|
| **Step1** | **ブログ記事追加・微修正（N-デザイン）** | 2週間 | 1. PR の質 2. Vercel Preview の使い方 3. コミットメッセージ規約理解 | コード品質・基本リテラシー |
| **Step2** | **小機能追加（Notエステの記事カテゴリ追加 or N-デザインの施工事例フォーム改修）** | 1ヶ月 | 1. 仕様読み解き 2. Supabase migration 作成 3. type 整備 | 設計力 |
| **Step3** | **やや重い改修（ファディーの基盤実装の一部）** | 1〜2ヶ月 | 1. ゼロから書く力 2. 質問・コミュニケーション頻度 3. 締切感 | 自走能力 |
| **Step4** | **本番障害対応シミュレーション**（CEO がテスト用Supabase に擬似障害を仕込む） | 1週間 | 1. ログ追跡力 2. 対応速度 3. クライアント向け説明文の質 | 緊急対応力 |
| **Step5** | **3〜6ヶ月の継続性チェック**（月次の小タスクを継続的に振り続ける） | 3〜6ヶ月 | 1. 連絡レスポンス低下しないか 2. 単発で終わらないか | 継続性 |

### 4-2. 評価軸（重みづけ）

| 評価軸 | 重み | 不合格ライン |
|---|---|---|
| **継続性**（連絡レスポンス・約束遵守） | **40%** | 平日24h以内に1次返信なし2回 = 不合格 |
| **コード品質** | 25% | Codex/Claudeレビューで critical 指摘3回連続 = 不合格 |
| **コミュニケーション**（仕様確認・ステークホルダー説明） | 20% | クライアント向け文章を書かせて確認 |
| **障害対応**（Step4 のシミュレーション） | 10% | 対応着手まで4h超 = 不合格 |
| **業務理解の伸び**（業務系のみ） | 5%（業務系のみ） | 法令・業界用語のキャッチアップ速度 |

### 4-3. 判定タイミング

- **3ヶ月**: Step1〜2 完了後に「続行 or 打ち切り」を判断
- **6ヶ月**: Step3〜5 完了後に「正式譲渡対象に確定」
- **9ヶ月**: クライアント紹介・三者会談・契約承継協議に進む
- **12ヶ月**: 移行二人体制スタート

→ **「2026年8月から探索開始→2027年8月に判定→2028年Q1に移譲完了」が最短**。これ以上タイトに組むと品質崩壊。

### 4-4. 候補者側にもメリットがある単価設計（重要）

| タスク種別 | 単価目安 | 根拠 |
|---|---|---|
| Step1 ブログ追加 | **時給5,000〜8,000円** | 副業層が動く最低ライン |
| Step2 小機能追加 | **タスク単価 5〜15万円** | 1ヶ月で結果出せる金額 |
| Step3 中規模改修 | **月額換算 20〜30万円**（時給6,000〜8,000円×40時間） | 副業フリーランスの希望帯 |
| Step5 継続保守（正式譲渡後） | **月額 15〜25万円/事業 × 引受事業数** | 業務系で月20〜35万円 |

**Step1〜3 は「テスト期間」と明示**しつつも、**フリーランスが時給換算で損しない単価を出す**こと。安く叩くと優秀層は離脱する。

## 5. 論点4: 戦略B が破綻した場合の代替案（C/D）

事業ごとに正直評価。

### 5-1. ビジネス21 — 戦略C（既製SaaS移行）の現実性

**実在性: ◯（JITCO サポートシステム実在）**

JITCOサポート（JITCO総合支援システム）が公益財団法人提供のクラウドSaaSとして実在。技能実習・育成就労（2026/4 制度改正）の書類作成、受入企業・実習生・送出機関の一元管理が可能。

**移行可能性: △（中程度）**

- メリット: 公的機関提供で信頼性最強・法令改正追随自動・既存ビジネス21の業務を概ねカバー
- 課題: クライアントが既にビジネス21カスタムシステムに業務フローを最適化済の可能性。**JITCOサポートへ業務フロー逆移植のコストが発生**
- 推奨判定: **戦略B 探索を半年やってダメなら戦略C 移行を本格検討**。並行で年内に「JITCOサポート機能比較表」を作成（writer に依頼）

### 5-2. トラスト — 戦略C（既製SaaS移行）の現実性

**実在性: ◯（複数選択肢実在）**

- らくしふ（LINE WORKS連携シフト管理）— 障がい者グループホーム導入実績あり
- 「ほのぼの」シリーズ（コニカミノルタ / リコー / キヤノンMJ / NDソフトウェア）— 障害福祉ソフトのデファクト
- ケアコラボ — 支援記録系SaaS

**移行可能性: ◎（高）**

- トラストは2026-08 本稼働予定で、まだクライアント業務がカスタムシステムに完全依存していない＝**移行コストが最も低い段階**
- らくしふ + ほのぼの の組み合わせで「シフト管理＋業務記録」をカバー可
- **advisor 強提案: トラストは戦略B より戦略C を本命に切り替えるべき**。理由:
  1. 24時間SLA を1個人/小規模事業者に引き受けてもらう難易度が高すぎる
  2. 福祉業界は「ほのぼの」シリーズが30年実績で、カスタム実装を引き継ぐ後継より既製SaaS+保守の方が安心される
  3. CEO の撤退タイムライン1〜2年に間に合う唯一のシナリオ

### 5-3. Notエステ — 戦略C

**実在性: ◯**

リザービア・ビューティーメリットなどサロン専用予約SaaSが多数。

**移行可能性: △**

- 予約機能だけならSaaS化容易。しかし Notエステは「ブログ・記事 CMS」を含む（`/studio`）。CMS部分は WordPress や STUDIO 等の汎用CMSへ別途移行が必要
- 戦略Bを優先しつつ、後継候補が見つからなければ「予約 = リザービア + CMS = STUDIO」のハイブリッド移行が現実解

### 5-4. N-デザイン・ファディー — 戦略C

**実在性: ◯（汎用CMSへの移行）**

工務店特化SaaSは弱いが、N-デザインは「コーポレートサイト+ブログ+施工事例」で汎用構成のためWordPress / STUDIO / Webflow / microCMS+Next.js 等への移行は容易。

**移行可能性: ◯**

戦略Bの後継候補が見つかれば最優先、見つからなければCへ。

### 5-5. 戦略D（クローズアウト）の倫理・法務評価

**結論: トラスト・ビジネス21 では実質不可。Notエステ・N-デザイン・ファディー では契約解除条項次第で可能**。

| 事業 | クローズアウト可否 | 理由 |
|---|---|---|
| **トラスト** | **❌ 不可** | 福祉インフラ。シフト管理停止＝夜勤回せず利用者ケア破綻。**社会的・倫理的に許されない** |
| **ビジネス21** | **❌ ほぼ不可** | 監理団体は外国人技能実習機構の指導監督下。システム喪失で受入企業の運営が停滞すると、技能実習生（労働者）の権利侵害に直結 |
| Notエステ | △ 可能（要事前通知） | エステ予約はLINE/電話に戻せる。3ヶ月前通知 + データエクスポート提供で誠実対応可 |
| N-デザイン | △ 可能（要事前通知） | コーポレートサイト停止は事業継続に致命的ではない |
| ファディー | ◯ 可能 | 再生成中で本番稼働前。完成前にクローズアウト判断は最も損失少 |

### 5-6. 「B も C も D も無理」のケース — 正直評価

**該当: トラストのみ**。

- B: 24時間SLA引受可能な後継が見つからない可能性 50%
- C: 福祉SaaS移行はクライアント（株式会社トラストエージェント）の同意が必要・現場スタッフ17名の再教育コストが発生
- D: 福祉インフラ停止は社会的に不可

→ **最悪シナリオ: トラスト1事業だけ撤退できず、2028年5月以降も由井が保守責任を負い続ける**

**回避策**:
1. **今年2026年内に「Cハイブリッド（らくしふ+ほのぼの+一部カスタム保守）」へ移行を CEO 主導で打診**。トラストエージェント側の不動産本業も忙しいので意外と受け入れる可能性あり
2. **譲渡対価でクライアントを後継エンジニアに引き渡す資金的余裕を作る**（事業引継ぎ支援金 100〜300万円規模）
3. **2028年5月の期限を厳守せず、トラスト1事業のみ2029年Q2 延長を許容**

## 6. 論点5: 1〜2年タイムラインの実現性

### 6-1. 1〜2年（〜2028年5月）— advisor の現実評価

**実現確率: 40〜50%**

| 事業 | 2028 Q1 完了確率 | ボトルネック |
|---|---|---|
| Notエステ | 60% | `/studio` 認証実装完成 + 後継1名 |
| N-デザイン | 75% | 本番PW強化 + 後継1名（サイト系で最易） |
| ファディー | 65% | 再生成完成 + 後継1名（仕様未確定の不確実性） |
| ビジネス21 | 45% | 監理団体業務理解できる後継が希少 |
| **トラスト** | **20%** | 24時間SLA・福祉法規・戦略C前提なら40% |

平均 = 約53%。**1事業以上は2028 Q1 に間に合わない確率が高い**。

### 6-2. 3年（〜2029 Q2）に延ばすと

**実現確率: 75〜85%**

- 1年余裕ができる → 戦略B が破綻した事業をCへ切替する時間が確保できる
- 後継候補プールも拡大できる（探索期間倍）
- クライアント側の業務フロー移行も丁寧に進められる
- **唯一の損失: 由井の保守拘束が1年延長**

### 6-3. 5年（〜2031 Q2）に延ばすと

**実現確率: 95%**

- 過剰。CEO のキャリア戦略上、5年は長すぎる
- 後継エンジニアにとっても「5年後の譲渡」は遠すぎてコミットしにくい
- **推奨しない**

### 6-4. 段階的撤退の現実性

**◎ 強推奨**。1〜2年で全事業同時撤退ではなく、以下の段階で:

| 期限 | 撤退対象 | 累積撤退率 |
|---|---|---|
| **2027 Q2** | 戦略A完了（グッぼる/プロギング/カラッと/みんなのWA） | 4/9 = 44% |
| **2027 Q4** | N-デザイン + ファディー（サイト系2本） | 6/9 = 67% |
| **2028 Q2** | Notエステ + ビジネス21（業務系2本） | 8/9 = 89% |
| **2029 Q2** | トラスト（SaaS移行完了 or 後継確保） | 9/9 = 100% |

→ **「2028 Q2 で89%撤退、2029 Q2 で完全撤退」が現実的なベストシナリオ**。

### 6-5. advisor の推奨タイムライン

CEO の希望「1〜2年で完全撤退」は**85% で破綻**。
**「2028 Q2 で大半撤退・2029 Q2 で完全撤退（実質2.5〜3年）」を新ゴールとして CEO 承認を得るべき**。

## 7. CEO へのリスク警告（無難を排して）

### 警告1: 「ぼやぼやしてると2028 Q1 にトラストだけ残る」

トラストは出口設計が最も難しい。今日から動かないと、他8事業の撤退が完了した2028 Q2 時点で「**トラスト1事業のためだけに由井が福祉インフラを抱え続ける**」状態になる。**最悪、5年延長確定**。今週中にトラストエージェント代表（臼井大典氏）と「将来的なSaaS移行（らくしふ+ほのぼの+一部カスタム）の打診」を非公式に行うべき。

### 警告3: 「フリーランス相場（月76〜94万円）と保守委託原資（月10〜25万円）の構造的乖離」

「Next.js+Supabase のフリーランス」を漠然と探すと**ほぼ全員に断られる**。なぜなら平均単価が月76〜94万円で、CEO が出せる月10〜25万円とは**1桁違う**。**ペルソナを明確化**:
- 「副業層」（本業会社員・週末稼働）
- 「地方フリーランス」（家賃低・単価妥協できる）
- 「成長中の小規模制作会社」（顧客獲得を求めている）

の3層に絞ったメッセージを出さないと反応ゼロ。

### 警告4: 「Notエステ `/studio` 認証実装が未完成のまま譲渡しようとすると後継から拒絶される」

未完成プロジェクトは引き受け手が見つからない。**2026年Q2 中に完成させてから探索開始**。逆に言えば developer タスクが律速になる。

### 警告5: 「Supabase 相乗りプロジェクト `uffodcgcpykrdawyeekx` の分離はトラスト分離より広い」

監査済（2026-05-19）でトラスト分離が前提条件と認識されているが、**5事業相乗り（n-design/みんなのWA/Notエステ/トラスト home-shift/trust_site）の全体的な分離計画が必要**。譲渡先が異なる事業を同一Supabaseプロジェクトに残せない。**「事業ごと別Supabaseプロジェクト」または「グループ単位の集約Supabase」への再編が、後継譲渡の物理的前提**。

### 警告6: 「契約承継条項のない既存契約は譲渡実行できない」

cfo へ別途依頼予定とのことだが、**契約承継条項を後追いで追加する各クライアントとの再契約交渉は事業ごと2〜3ヶ月かかる**。これも律速要因。2026年Q3 中に全クライアントと再契約完了させないと、2028 Q1 譲渡実行に間に合わない。
