## 実行モード（全プロンプト共通）

このプロンプトでアプリを実装・改修・反映する依頼は、設計図・計画書・比較案の承認待ちで終えない。必要最小限の調査後に実装、検証、commit/push、本番デプロイと実URL確認まで進める。SNSの実投稿は、このプロンプト固有の明示承認境界を優先する。詳細は C:\Project\docs\execution-first.md。

# Reel App Server Prompt

このプロンプトは、現在の事業フォルダにある `AGENTS.md`、`CLAUDE.md`、`README.md`、公式サイト、ローカル素材、既存リール、`判断.md`、`sns-posting.md` を読み、その事業専用のInstagram Reels / Threads作成App Serverを実装・運用するために使う。

制作・投稿要件の正本は、実行環境で有効な `myreel` Skillとその参照資料とする。全文を読み、この管理画面用契約へ反映する。myblog記事が元なら `myblog` のReel連携要件も適用する。

## 絶対ルール

- 投稿先は必ず `判断.md` で確認し、推測しない
- 事業またはInstagramアカウントが未登録・複数候補なら、投稿先を推測せず `posting_account_status` に表示する。企画・素材・プレビューは下書きとして作成できるが、投稿画面への入力と公開は登録・確認まで止める
- 別事業のトークン、API、投稿キュー、ストレージを流用しない
- 生成と投稿を分離し、人間の明示承認前に投稿しない
- 制作中のローカル作業状態とInstagramの下書きを区別する。Instagram下書きには保存せず、投稿依頼と最終投稿セットの承認が揃った場合だけ直接公開する
- InstagramだけでなくThreads本文も必ず作る
- 認証情報を画面、ログ、JSON、チャットへ出さない

## 最初に確定する情報

- 事業名、投稿先Instagram / Threadsアカウント
- 誰に向けるか、何の悩みを解決するか
- 元になるブログ記事、任意テキスト、URL、承認済み動画・写真、生成動画brief、現場メモ
- 投稿目的: 認知、予約、相談、参加、商品確認
- 必須CTAと最終URL
- 使用を避ける画像、表現、医療・法律上の注意

## 作成フロー

### 1. 素材とトレンドを調査する

- ブログ、任意テキスト、URLまたはローカル素材から、本文、画像、商品、場所、人物、具体的な数字を抽出する
- その事業の既存リールを確認できる場合は、再生数を方向性の参考にし、画角、被写体、最初の1秒、文字量、CTAを分析する
- 公開再生数をリーチ、保存、成約と呼ばない
- 4〜5枚の適切な画像、承認済みの提供動画、または承認済みの生成動画briefを選ぶ
- 適切な素材が4枚未満なら、勝手に外部画像を追加せず確認事項にする

### 2. リール企画候補を3つ作る

1. 悩み→現場の工夫→次の一歩
2. 失敗→修正→改善後の流れ
3. 初回利用・来店・参加の流れ

各候補に、対象者、解決する悩み、冒頭フック、使う素材、CTAを付ける。管理者が1案を選び、編集してから生成できるようにする。

### 3. 9:16リール動画を構成する

- 1080×1920の縦長9:16
- 通常は5つの大きなセンター文字を構成し、各場面の文字を自然に読める表示時間を確保する。myblog記事連携では、内容紹介の場面と必要な後続場面を作り、5場面・15秒に固定しない
- 素材数と場面数は分け、承認済み素材の再利用または動画内の別区間で構成する
- myblog記事連携のナレーションは、各場面のセンター文字を省略・要約・言い換えず全文読み、対応表と一致結果を残す。尺を延ばし、読み上げを速めない
- myblog記事連携では、再現可能な自作または事業所有の原曲・非ボーカルBGMを基本とする。第三者音源は個別承認と利用権確認がある場合だけ使い、ナレーションより十分小さい音量とダッキングの両方をQAする
- 被写体をスマホで十分大きく見せ、余白だらけの画像にしない
- 横長・正方形画像は、全画面クロップ、ぼかし背景、被写体を大きくした安全クロップで最適化する
- 文字は画面中央、大きな白文字、細い黒アウトライン、透明背景を基本とする
- 1フレーム最大3行。Instagram UIに隠れない安全余白を取る
- 画像内の人物、商品、設備を文字で隠さない
- 指定ブログ、テキスト、URL、承認済み素材から全画面動画を生成する
- 動画生成APIを使う場合は非同期ジョブとして進捗を表示し、完成MP4を取得する
- 生成動画内の文字表現へ依存せず、正確なセンター文字は決定論的な最終レンダーで焼き込む。配色・縁取りは確認した事業の文字ルールへ合わせる

### 4. 投稿文とカバーを作る

- Instagramキャプション: 固定文字数にせず、対象者、内容量、投稿目的、対象アカウントに合う読みやすい長さで、短いタイトル、本文、CTAをまとめ、最終URLを必ず末尾に置く
- Threads本文: 1つの主張、具体例をまとめ、最終URLを必ず末尾に置く
- ハッシュタグは必要な場合だけ少数
- カバー画像は、1秒で内容が分かる短い見出しと、主役が大きく見える画角にする
- 事業ごとにレイアウト・書体・配色・ロゴ位置が揃う1080×1920の統一カバーを作り、プロフィール一覧の正方形プレビューでも文字と主題が残ることを確認する
- 投稿依頼時の標準セットはReel、下部に `詳細はこちら` の確認済みURLリンクを置くストーリーズ共有、店舗自身のコメントとし、各文面も最終レビューへ含める
- InstagramとThreadsで別人格にせず、同じ実践知を媒体向けに再編集する

### 5. 投稿前プレビューを出す

- スマホ9:16のフレームプレビュー
- 使用素材一覧
- 各フレームの表示文、秒数、クロップ方針
- Instagramキャプション
- Threads本文
- カバー画像
- 最終URLとCTA
- 投稿先アカウント
- 即時投稿または予約投稿の選択
- 全場面の画面テキスト、キャプション、CTA、URL、動画調整プロンプトをすべて編集可能にする
- 最後に自由な調整プロンプトを入力し、動画の被写体、画角、動き、色調、テンポへ反映できるようにする

### 6. 投稿マニフェストを作る

`mode` は最初は必ず `preview`。各投稿には次を含める。

ここでの `status: draft` はローカル制作データの状態であり、Instagram下書きの保存指示ではない。

- `campaign_key`
- `timezone: Asia/Tokyo`
- `idempotency_key`
- `platform`
- `status: draft`
- `caption`
- `media`
- `cta`
- `source_refs`
- `approval.required: true`
- `approval.approved_by: null`
- `approval.approved_at: null`

### 7. 投稿画面へ誘導する

- 「Instagramキャプションをコピー」ボタン
- 「Threads本文をコピー」ボタン
- 「Instagram投稿画面を開く」ボタン
- 「Threads投稿画面を開く」ボタン
- 投稿先が `判断.md` に未登録なら、投稿画面ボタンの近くに「アカウント未登録・要確認」を明示する
- 投稿画面を開くことと、投稿を実行することを分ける

### 8. 投稿前の人間確認

次を1画面にまとめ、「この内容で投稿してよいですか？」と確認する。

- 事業名、Instagram / Threadsアカウント
- 元URLまたは素材パス
- 最終動画、カバー、使用画像
- Instagramキャプション、Threads本文
- CTA、URL、投稿日時
- 効果保証なし、医療・法律上の過剰表現なし、未承認画像なし、別アカウント誤投稿なし、URL欠落なし、認証情報表示なし

明示承認がない限り、Meta Graph APIの投稿処理を実行しない。

myblog記事から作った場合は、投稿承認前に同じ最終MP4と統一カバーを元記事の `authorship_note → video → hero` の順で表示し、記事・静的動画の本番URLを確認する。承認済み投稿セットは同じ事業アカウントへ続けて実行し、同一内容の重複承認を求めない。ブラウザでストーリーズ共有やリンク操作ができない工程は未完了として引き継ぎ、Reel・ストーリーズ・コメントそれぞれの実結果を記録する。

## 出力契約

- `concept_candidates`: 必ず3件
- `selected_concept`
- `frames`: 通常5件、myblog連携時は読了に必要な可変件数。text、duration、media、crop、safe_area。textは各3行以内
- `video`: generation_prompt、job_id、status、progress、mp4_urlまたはローカルパス
- `final_adjustment_prompt`
- `cover`: title、media、preview
- `instagram_caption`
- `threads_caption`
- `story_text` / `story_link` / `shop_comment`: 標準投稿セットのレビュー内容
- `source_article`: myblog連携時の元記事URL、同一MP4・統一カバーURL、配置・PC/スマホQA
- `cta` / `final_url`
- `manifest`
- `approval_checklist`
- `posting_account_status`
- `publish_logs`: 投稿を試した場合だけ追加し、トークンは保存しない

## 保存場所

採用するリール素材は、事業フォルダ内の `content/campaigns/YYYY-MM-DD-topic/` にまとめる。README、元URL、選択素材、最適化画像、台本、キャプション、動画、カバー、プレビューHTML、マニフェスト、投稿前確認を残す。
## 画面・キー・Chrome投稿要件（2026-07-13）

- リール制作UIは、ブログやコンテンツを運用する各サイトの既存認証済み管理画面内へ、そのサイト自身のURLと静的資産として配置する。共通 `/studio`、外部App Serverリンク、新しい中央タブ、iframeへ管理者を誘導しない。
- `_shared/blog-app-server` の `/reel`、`reel.html`、`reel.js` は同期元とAPI検証用の正本であり、運用者の共通入口にはしない。各サイトでは事業IDと登録済み投稿先を固定し、別事業へ切り替える選択欄を出さない。ブログとリールは同じ管理セクション内の別タブまたは別ローカルルートにする。
- OpenAI APIキーはリール画面のパスワード型入力欄で入力し、管理画面ログイン用パスワードとは別に扱う。入力キーはブラウザの `sessionStorage` にだけ保持し、`localStorage`、Cookie、IndexedDB、サーバーファイル、Git、HTML、ログ、Skillへ保存しない。
- 保存前に認証済みの `/api/key/verify` からOpenAI APIへ検証リクエストを送り、成功したキーだけライブ生成に使う。検証失敗時は直ちに `sessionStorage` から削除し、ライブ生成を無効にする。
- 企画生成、Sora動画生成、状態確認、動画取得の全工程で同じ検証済みセッションキーを `X-OpenAI-API-Key` ヘッダーだけで使い、本文、URLクエリ、マニフェスト、出力ファイルへ含めない。
- 検証済みブラウザキーがない場合だけ、サーバー側の `OPENAI_API_KEY` をフォールバックとして使用できる。サーバー側キーはブラウザへ返さない。どちらもない場合はデモ表示にする。
- この制作画面はブラウザによる投稿準備を扱う。無人API投稿はSNS自動化Skillの別工程とする。
- ブラウザでの公開・送信は、[共通ルールの公開・送信と停止条件](C:/Project/docs/browser-account-policy.md#公開送信と停止条件)に従う。
- 完成したリール下書きは `contentStudioReelDraft:<profileId>` の共通handoff契約またはサイト固有の保存adapterで既存管理画面へ戻す。投稿は自動実行しない。
- native rollout manifestに対象サイトを登録し、ローカルUI未配置、旧中央URL、iframe、別事業profileが残る場合は検証を失敗させる。
